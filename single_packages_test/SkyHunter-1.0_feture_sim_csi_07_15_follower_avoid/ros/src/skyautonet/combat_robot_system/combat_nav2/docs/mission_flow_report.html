미션 데이터 흐름 설계서

Tablet → command_server → mission_control_node → Nav2 → 차량

대상 패키지: combatrobot_1/robot_server · combat_nav2/combat_robot_nav2  |  메시지 패키지: combat_robot_msgs  |  작성일: 2026-06-01  |  ROS 2 Jazzy / Nav2

1. 개요

태블릿 앱이 그린 GPS 경로(웨이포인트 목록)를 차량이 자율주행으로 순회하기까지의 전체 데이터 흐름을 정의한다. 경로 명령은 태블릿에서 TCP 바이너리 프로토콜로 차량 측 command_server(combatrobot_1)에 전달되고, ROS 토픽 /swarm/path_command로 변환되어 mission_control_node(combat_nav2)로 넘어간다. 이 노드가 위경도를 /fromLL 서비스로 map 좌표로 변환하고, Nav2의 NavigateToPose 액션으로 웨이포인트를 하나씩 순차 주행시킨다. 최종 속도 명령은 /cmd_vel로 차량 모터(CAN)에 전달된다.

명령 체계는 LOAD_PATHSTARTPAUSERESUMESTOP 5종이며, 본 문서 기준으로 PAUSE/RESUME 까지 mission_control_node 에 구현 완료되었다.

3. TCP 프로토콜 (Tablet → command_server)

태블릿은 PATH_PORT(65436)로 접속해, 고정 7바이트 헤더 뒤에 (LOAD_PATH 일 때만) JSON 페이로드를 붙여 전송한다. 헤더는 #pragma pack(1) 로 패딩 없이 직렬화된다.

3.1 AssaultCommandHeader (7 bytes, packed)

오프셋필드타입크기설명
0commanduint81명령 코드 (아래 표)
1num_waypointsuint162웨이포인트 개수 (페이로드와 교차 검증)
3data_lengthuint324뒤따르는 path_json 바이트 수 (없으면 0)

3.2 명령 코드 (AssaultCmdType)

값명령페이로드command_server 처리
1CMD_START없음path_loaded 확인 → 미션 MOVING, 홈 좌표 캡처
2CMD_STOP없음미션 실행 리셋, 상태 NONE
3CMD_PAUSE없음MOVING 일 때만 PAUSED, 속도 0
4CMD_RESUME없음path_loaded 확인 → MOVING 복귀
5CMD_LOAD_PATHpath_json웨이포인트 파싱·개수 검증·캐싱 후 발행
검증 게이트: command_server는 num_waypoints(헤더)와 path_json에서 추출한 실제 개수가 다르면 WAYPOINT_COUNT_MISMATCH로 거절하고 발행하지 않는다. 또한 START/RESUME은 경로 미적재 시 PATH_NOT_LOADED로 거절한다. 검증을 통과한 명령만 /swarm/path_command로 재발행된다.

4.2 path_json 지원 포맷

mission_control_node의 parsePathJson()는 의존성 없는 경량 파서로 3가지 포맷을 지원한다.

포맷예시
객체 배열 (waypoints 키){"waypoints":[{"lat":37.4,"lon":126.7}, ...]}
GeoJSON coordinates{"coordinates":[[126.7,37.4], ...]} (lon,lat 순)
최상위 배열[{"lat":37.4,"lon":126.7}, ...]

키 별칭 지원: 위도 lat/latitude, 경도 lon/lng/longitude

5. 정상 / PAUSE·RESUME / STOP 시퀀스

그림 3. LOAD_PATH→START 주행, 중간 PAUSE→RESUME, STOP 시나리오

  • 경로 적재: LOAD_PATH → parsePathJson() → pending_path_ 에 캐싱 (주행 시작 안 함)
  • 미션 시작: START → start_mission(), active_index_=0, 웨이포인트 루프 진입
  • 웨이포인트 루프: /fromLL로 좌표 변환 → NavigateToPose 전송 → SUCCEEDED 시 active_index_++ → 다음 wp
  • 일시정지: PAUSE → 현재 goal cancel(인덱스 유지), RESUME → 현재 wp부터 재플래닝하여 재개
  • 중단: STOP → goal cancel, 상태 전체 리셋(pending_path_ 포함)

7. PAUSE / RESUME 구현 상세

Nav2 NavigateToPose 액션에는 네이티브 "일시정지"가 없다. 따라서 다음 전략을 택했다.

설계 원칙: PAUSE = 현재 goal 을 cancel(웨이포인트 인덱스는 보존), RESUME = 보존된 인덱스의 웨이포인트로 goal 재전송. 단순히 /cmd_vel만 막는 방식과 달리 Nav2가 "주행 중"이라고 착각하지 않고, 재개 시 현재 위치에서 다시 경로를 계획하므로 더 견고하다.

7.1 핵심 상태 변수

기존 active_(미션 실행 중)에 더해 paused_ 플래그를 추가했다. PAUSE 로 발생하는 CANCELED 결과를 미션 실패(STOP)와 구분하는 것이 핵심이다.

bool active_ = false;   // 미션 실행 중 (PAUSE 중에도 true 유지)
bool paused_ = false;   // PAUSE 로 현재 goal 을 cancel 한 상태 (active_index_ 유지)

7.2 명령 처리

case CMD_PAUSE:
    if (!active_ || paused_) return;            // 주행 중 아님 / 이미 정지
    paused_ = true;
    if (active_goal_) nav_client_->async_cancel_goal(active_goal_);
    break;                                       // active_index_ 는 유지

case CMD_RESUME:
    if (!active_ || !paused_) return;           // 미션 없음 / 정지 상태 아님
    paused_ = false;
    execute_next_waypoint();                     // 동일 wp 부터 재개
    break;

7.3 경합(race) 방어

PAUSE 가 비동기 콜백 경계 어디에서 도착해도 안전하도록 세 콜백에 가드를 추가했다.

PAUSE 도착 시점처리 (방어 코드)
/fromLL 응답 대기 중from_ll_response_callback: paused_면 goal 전송 보류 (RESUME 시 재요청)
goal 전송~accept 사이goal_response_callback: paused_면 accept 된 goal 즉시 cancel
주행 중 (goal active)result_callback: paused_면 CANCELED 를 실패로 처리하지 않고 RESUME 대기
STOP 과의 차이: STOP은 cancel_mission()에서 active_=false, paused_=false로 전체 리셋하고 pending_path_까지 비운다. PAUSE는 active_를 유지하고 인덱스를 보존한다는 점이 다르다. 콜백들은 active_(STOP)와 paused_(PAUSE)를 각각 먼저 검사해 늦게 도착한 결과를 올바르게 무시/보류한다.

8. 향후 과제 / 주의사항

  • 상태 피드백 역방향 채널: 현재 Nav2 → command_server 로의 실시간 진행률/도착 상태 환류는 mission_control_node 기준 로깅 위주다. 태블릿 표시용 mission_status 동기화는 command_server 자체 상태에 의존한다.
  • PAUSE 중 cmd_vel: goal cancel 방식이므로 Nav2가 즉시 정지 명령을 내보내지만, 컨트롤러 감속 프로파일에 따라 완전 정지까지 짧은 지연이 있을 수 있다.
  • 테스트 입력 경로: /mission_input(WaypointList) 직접 입력 경로는 디버그용이며 PAUSE/RESUME 흐름과 무관하다.
